1. Creating ‘Mundus Ulterior’
Heading: The story behind ‘Mundus Ulterior’
This ‘Methodology’ page explains how I built ‘Mundus Ulterior’: the sources, their processing, the tests, the limitations, and tooling. I also include future improvement recommendations.
The answers on this site are pre-loaded. Before answer generation, I fixed the questions, the source each one should find, and whether each should be answered or declined. The answers were then generated and scored against those expectations. They were also validated against their sources. Almost every quotation resolves to a specific range of characters in its source, which can be opened and read in full. Those that don't are shown with the reason. In most cases, the system (detailed below) worked very well. However, I’ve deliberately kept the few failures, both to illustrate the current limitations, and as a guide for future improvements.

2. Source compilation
Heading: Where does the data come from?
For this project, a record is a single source. It holds the source's own words, where they can be obtained, a published translation (when available), a museum's catalogue description, or a pointer to where the text is held (see the tiers below). Records may also include citations to original/translated versions, and notes on text capture.
Record candidates were named before being curated. Each sourcing round started by listing regions, the evidence sought and whether each source could be reached. The final round also listed the expected reuse rights. Sources that were considered and rejected are documented, with the reason for each, in the project's working records rather than on this site, because even discarded candidates reveal important limitations. Some rejected candidates were later reconsidered and added. Refused candidates spanned many reasons: bot blockers, login portals, redirect loops, and paywalls. Because evidence types differ, records are sorted into tiers:
* Source text with a published translation: the source's own words and a human translation, both cited. The strongest thing in the corpus.
* Source text, machine English: the source's own words, but no reachable published translation. The claim is reachability, not existence: each record in this tier is meant to state the search that failed and where it stopped, and not every record yet does.
* Published translation only: a published translation is held, but no open transcription of the source's own words could be obtained, even where one exists in print.
* Catalogue record: a museum's object description, which is not the object speaking.
* Pointer: the record does not carry the text itself, but states exactly where the text is held and how to find it.
Reading a source and being allowed to quote it are two different facts, which are recorded separately.
Copyrighted text is quoted only where the quotation is short and bounded by the source, the work is fully cited, the terms are stated in the record in the source's own words, and the use is non-commercial research. Terms have been read and recorded for every source. Where a source's terms restrict use to personal study, its text is taken from a public-domain edition of the same work instead; no source has been excluded on its terms.
Terms are read off the object being quoted, and the rest of the site where needed, and copied in verbatim with the address, the reader and the date. No reuse position is inferred from the record's own description or by text-matching.

3. Preparing the data
Heading: Preparing the sources for search
Each source is cut into passages and each passage is vectorized (given a numeric representation of its meaning). These vectors are loaded into a database that can be searched by similarity based on the following steps:
Splitting. Only texts longer than a set maximum length are split, and every cut falls on a boundary the source itself provides: section markers first, then paragraphs, then line breaks, then sentence endings (Latin and Chinese sentence punctuation). No text is cut mid-sentence to fit a length, which avoids producing unintelligible passages. Most sources are short enough that no splitting was needed. Fragments below a minimum length are merged back into their neighbours.
Character positions. Every passage records the exact character positions it occupies in its source field. The system repeatedly verifies that the characters sitting at those positions are the characters the passage holds. This is what makes citations openable and directly readable.
Language, checked against the script. Each passage carries the language a curator declared. When the data is loaded, that declaration is checked against the writing system the text is actually in, and a passage whose script does not match its declared language is refused rather than stored, so a mislabelled language cannot reach the search.
Original and translation stay separate. A source's own words and its published English translation become separate passages, each marked as belonging to the same record, rather than being merged. When an answer is written, the two are paired again. Keeping them apart is what makes it possible to test whether the source-language text can be found on its own, without the English answering for it.
Numeric representation. Each passage is converted into a list of numbers (embeddings, which carry meaning rather than its spelling). Passages about similar subjects end up close together even without shared characters, which allows an English question to reach a Chinese passage. Embeddings are produced by a commercial model (Voyage AI's voyage-3.5) reached through a single internal gateway, so the model can be changed in one place.
Places. Geographic coordinates are not written into a source record. Where a source names a specific place, the record stores that place's identifier in a published gazetteer (a reference list of places, each with a stable identifier and usually a location). A single component resolves identifiers into points, reading from a dated snapshot of the gazetteer. Identifiers are never written from memory, by a person or by a model.

4. Building the retrieval system
Heading: How questions find their passage
The basic path. A question is converted into the same kind of numeric representation as the passages, and the system returns the passages closest to it in meaning. There is no translation step and no keyword matching when an answer is produced.
Why it works across scripts. The model (voyage-3.5) that produces those representations was trained across many languages, so a question in English and a passage in Literary Chinese can land near each other without sharing a character.
How that claim is tested. For some of the test questions, English translations are removed from the pool of candidates before the test runs; the rest are tested with the translations still in place. With the English available, an English question finds the English, which proves nothing about the source-language text. With it removed, the question either reaches the original or it does not.
Early tests reported both whether the correct source was found and whether its non-English text was reachable. The second figure was lower. Padding the collection with plausible but irrelevant English material made no difference to the results at any size tested. The fall in non-English results came later, as more real sources were added: English-language targets held steady while non-English targets were found less often.
Nothing is generated while you read. Every answer on this site was produced in advance and is replayed from storage, then re-checked against the current sources. Live answers, which are beyond this project’s scope, would need to be evaluated each time and for every question and answer.

5. Building the harness
Heading: The rules, and the checks that enforce them
Two kinds of written decision. A ruling is a rule the project adopts, recorded with its reasoning and rejected alternatives. Rulings are written before the work they govern. A finding is something observed, usually a defect. Rulings are decided; findings are discovered. Both are numbered, and rulings are indexed in a single register.
Checks. Automated tests run against a reference version kept in the project repository: they execute its code, render every stored answer, and compare what appears against the data it describes. By rule, a failure blocks the change. Everything this page says about how the site is built describes the reference copy: the version kept in the project repository, which the checks run against. Any hosted version is built from the same data file, and checks that inspect rendered output run against the reference copy only. Incompletions are clearly noted.
Practices.
* Predictions before code. Each stage records what it expects, commits that record before any code is edited, and scores it afterwards without amendment. One prediction per stage is written not to flatter it.
* Checks are seen to fail first. A new check is deliberately broken before it is trusted. This has repeatedly found the fault in the check rather than the code.
* No figure is typed into the page. Counts are computed from the stored data, in digits and in words alike.
The limit. Numbers are recomputed on every build and cannot go stale. The sentences around them are typed once and never re-checked, so a sentence can stop being true while the number beside it stays correct. Where a sentence can be generated from the data instead, it now is.

6. Quality tests
Heading: What is tested, and how
Citations. Every quotation in every stored answer is re-checked against the current sources and sorted by what was found:
* the characters are exactly as quoted;
* they differ only in capitalisation, and the record says so;
* they differ only in capitalisation, but the record claims an exact match (a labelling defect, left visible rather than corrected);
* they differ only in spacing;
* the quotation is still in the file, at a different position;
* the quotation is no longer in the file.
Whether the source itself changed. Mismatches have two identical-looking causes: the citation was wrong, or the source was edited after the answer was stored. Most stored answers record a fingerprint of every source they quoted, so the two can be told apart: unchanged means the mismatch is a real defect, changed means it is explained, and no fingerprint recorded means it cannot be determined. The third is kept separate since counting it either way would invent defects or explain them away.
Retrieval is scored against known ‘good question-and-source pairs’: whether the correct passage appears near the top, how far down it is, and its margin over whatever outranked it are reported two ways, since being beaten by a related passage of the same source is a different failure from being beaten by an unrelated one.
Translation is checked by translating a passage into English, translating that English back in a separate request that never sees the original, and comparing closeness of wording and closeness of meaning. Thresholds are set where no observed case falls near the line. Only the pass mark for prose has been set that way so far; the others are provisional.
Places. No specific place is accepted unless it resolves through a dated snapshot of a published gazetteer. Nothing invents a point, matches on similar names, or substitutes a regional centre; every failure stops the process.
No model judges another model's output. Every assertion in the scoring is a fact about text: this string appears, this identifier is among the cited sources. An uncalibrated model with no rubric marking another model's work could be wrong in the same direction and agree with it.

7. Creating the portal
Heading: How the portal was built
The reference copy of this site, the version kept in the project repository and checked by the tests, is built as follows:
* One hand-written HTML page that opens directly from disk, alongside a generated data file and the masthead images. The page itself uses no framework, is not compiled or bundled, needs no server and loads nothing from outside; the data file and images are produced beforehand by scripts in the repository.
* Every colour, and most size and spacing values, is a named token rather than a number written into the markup.
* The masthead shows short specimens from the records in {{derived: number of scripts in the masthead}} writing systems, some as romanised transcriptions, rendered as images so that a visitor without the relevant fonts installed does not see empty boxes. Each image is drawn in a single colour and inverted for the dark theme, so one file serves both.
* Which sources appear in the masthead is a curation decision, declared in the page's code and checked against the script that draws the images. The characters shown and the alt text are read from the records.
* The map is drawn as SVG by the page's own code, from a dated public coastline dataset and the gazetteer positions, with its own solver that hides any label that would overlap another.
* A separate instrument measures the page's layout. It reports whether a figure moved and has no opinion on whether the page is better: a change that improved every measured figure once made the page worse to read and was reversed on human judgement.

8. Limitations, gaps and failures
Heading: Limitations and failures
Retrieval is tested against questions whose correct source is already known. For English sources, the system has found the correct source in almost every test run. The exception is the record of a carved gemstone from Khao Sam Kaeo in Thailand, which has never been found. For original language sources, results got worse as the collection grew. Of all the languages tested, Old Tamil performed worst at every stage run on the project's standard model, claude-haiku-4-5. The stronger model, claude-sonnet-5, has been tested only on rewriting questions into Old Tamil, and it succeeded every time. When an English question is searched, the Old Tamil passage it should find ranks far below where it should. When a question already written in Old Tamil is searched, the passage ranks first, but with the weakest similarity score of any script tested. In the round-trip translation test on the standard model, some attempts came back in the wrong script entirely; the stronger model has not been tested on translation. When the standard model rewrote the test questions into the collection's languages, almost every rejected rewrite was in Old Tamil: the model wrote in other South Asian scripts instead, such as Devanagari, Malayalam, Sinhala or Bengali. Why this happens has not been established. Nothing reported these results separately by language, so the decline went unnoticed for several rounds of work.
The site lists the questions it holds answers for. A few are held back. Those are named here with what went wrong, because a question that never produced an answer is a different problem from one that produced answers without ever quoting a source. The page also names whichever question is currently answered worst.

The map leaves out more than it shows. When a source names a region rather than a town, the map shades that region's area instead of placing a point. When it names a people, an office or an empire, that is recorded and no position is drawn; the record still appears on the map as a square in its region's band. The Chinese records naming Rome, the sources closest to the point of this project, cannot place Rome on the map. The names they use (Da Qin, and later Fulin) describe a state and its people rather than a city, and for at least one record the published translators disagree about which country is meant; drawing a single point would claim more than the texts say. Most of these records appear on the map only as squares in the East Asia band.

Known and unfixed:
* For every failed quotation currently shown, the cause cannot be explained. Answers only began recording which version of a source they used partway through, so for the rest there is no way to tell a wrong quotation from a source edited afterwards.
* Some stored answers no longer hold the full text of the passages they were given. The page says so where that is true.
* The translation checks are mostly uncalibrated. Nearly every source turned out to have a published English translation, so the machine translation those checks exist to judge almost never ran.
* Improvements to the search were built and used in testing, then dropped: combining each original passage with its translation, and re-ranking results with a second model. Nothing records the decision. Neither was ever used to produce the answers on this site, and the results reported here come from the version without them.
What the project decided it could not do. An expansion to a much larger collection was planned, with decision gate criteria set in advance. Based on the results, corpus expansion plans were dropped rather than postponed. That said, corpus scaling and diversification can still take this project to new levels (see next section).

9. Ideas for future development
Heading: Ideas for taking ‘Mundus Ulterior’ to new levels
Report results by language as the test runs. The evidence under Limitations is derived here, on this page, from the archived runs; the test itself still prints a single total, so the one measure that has been moving is invisible at the moment a change is made. Moving that split into the test is a small job, and it is what would let the next change to the collection be judged while it is being made.
Add more sources, in the languages that fail. More material in the languages where retrieval is weakest remains the obvious improvement, but the last expansion made those results worse. The likely cause is that each new source adds passages, including English translations, which compete with original-language targets for the top positions. That would need to be addressed before the corpus grows further, so that adding sources does not undo the gain.
Adding Roman Imperial sources. Most of what is here is the view from outside the empire, although some sources, such as the Periplus and the writings of Cosmas Indicopleustes, were written inside it. The complement is a deliberate set of Roman and Eastern Roman (Byzantine) sources about these same regions, set beside them: the same objects, routes and embassies, described from both ends. Two accounts that disagree are better evidence than either alone. The site can already show several sources in one answer, but a view built for comparing them side by side would be new work.
A longer span. The current window runs from the founding of the Roman Empire in 27 BC to the sack of Constantinople in 1204 AD. An earlier window would cover potential Roman Republic connections and a later window would follow the Eastern Roman relationships ending with the Ottoman conquest in 1453.
Let specialists correct it. The highest-value change is not technical. Someone who reads Geʿez, who has excavated one of these sites, or who knows which of two competing identifications the field has settled on could correct things nobody here can check. The structure for that already exists: the placements recorded as disputed, and the sources whose terms have not been read, are both places to disagree on the record. Specialists sending corrections are an obvious addition here.
Material that exercises the translation checks. As noted under Limitations, the translation checks almost never ran, because nearly every source already had a published English translation. Sources without a published translation are what would make the checks active and let their thresholds be set from observation rather than left provisional.
A chat search function. There is none yet, mainly because of cost. A live answer needs a search and a model call for every question, and the services' usage limits would have to be sized for public traffic. The harder problem is presentational. Each answer here was generated in advance and scored against expectations set before it was generated. A live answer can be checked against its sources as it is written, as every answer here was, but it would need to be scored and presented differently from the prepared questions. That is doable, but it was not in scope.

10. Tooling and techniques
Heading: The Mundus Ulterior tech stack
Server side. Python. PostgreSQL 16 with the pgvector extension as the store, running in a container. Every model call (text generation and embeddings) passes through a single LiteLLM gateway, so a model is swapped in one place and adding a second never silently repoints the one existing measurements were taken on.
Models.
* Answer assembly, translation, and rewriting test questions into the collection's languages: Anthropic claude-haiku-4-5. A stronger tier, claude-sonnet-5, is available where a run names it and was used to re-test the Old Tamil rewrites. It is a second option rather than a replacement: repointing the first would make every stored measurement incomparable.
* Embeddings: voyage-3.5, at 1,024 dimensions. The same model converts the stored passages and the incoming question, which is what puts them in the same space.
* Re-scoring search results: Voyage rerank-2.5, used in retrieval testing only and not in producing the answers on this site (see Limitations).
* Rejected: a locally hosted re-scoring model, because a hosted service did the same job for less cost and effort; and an open embedding model (BGE-M3), planned as a replacement and dropped because voyage-3.5 passed every cross-language test it was given.
* No model judges another model's output anywhere in this project.
Cost of an answer. One embedding request and one text-generation call. The embedding service started on a free tier with a very low limit on requests per minute and was later moved to a paid tier. Every answer here was produced in advance, so a visitor's reading never depends on those limits or costs.
Front end (reference copy). One hand-written HTML page, plus a generated data file and the masthead images: no framework, no bundler, no content delivery network and no server, and the page itself is not compiled. The data file and images are generated by scripts beforehand. The page is a set of plain functions returning HTML, which is what lets the checking script execute the page's own code and inspect what it produces.
The data file the page loads is generated and never hand-edited. It joins stored answers to source records so the page can show the characters a citation points at, rather than the positions alone.
Testing. Hand-written runners rather than a test framework. Much of it is mutation testing: defects are introduced deliberately, and the check meant to catch each one is confirmed to fail before the check is trusted. Playwright with headless Chromium measures the page's layout. A single script runs the core checks and prints the results, with no way to supply a figure by hand.
Build environment. Developed in sessions with Anthropic's Claude, in Cowork. The sandbox cannot commit, so each commit is an instruction carried out by hand. A file write reported success without taking effect, more than once, and the checks then passed against the old file. So before anything is run against a changed file, its size, or a string the change introduced, is checked first.
